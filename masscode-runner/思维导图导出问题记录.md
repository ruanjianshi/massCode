## 4. 修复尝试时间线（重要：吸取教训，勿重蹈覆辙）

markmap 渲染结构要点：
- `svg#mm-svg` 尺寸 = 容器视口（CSS 100%），**无 viewBox**；
- 第一层子元素：`<style>`（markmap 自带 CSS 变量）+ 主 zoom 层 `<g>`，transform 形如 `translate(134.5,234) scale(2)`；
- 每个节点 `<g class="markmap-node" data-depth="N" transform="translate(x,y)">` 内：`<line>` + `<circle>` + `<foreignObject class="markmap-foreign" x="8" y="0">`（**foreignObject 的 x/y 是相对所属 node g 的局部坐标**，真实位置 = node g translate + 局部偏移）。

### 第 1 版（原始实现，用户报"没包揽"）
直接把 svg `cloneNode(true)` 序列化导出。**问题**：内容带 `translate+scale` 变换 + svg 无 viewBox → 导出 = 当前视口的一小块，整棵树超出部分全部丢失。

### 第 2 版（用户报"还是没囊括"，实为文本重叠）
clone 后**移除主 zoom 层 transform** → 内容回数据坐标 → 挂载隐藏 div 用 `getBBox()` 遍历 `path,circle,line,rect,ellipse,text` 算内容包围盒 → 设 `viewBox` + width/height。
文字转换时直接取 `fo.getAttribute('x')/('y')`（相对坐标）→ **没叠加 node g 的 translate → 27 行文字全部堆在 (8, 9.6) 原点叠成乱码**。几何验证"内容在 viewBox 内"虽通过（path/circle 的 bbox 正常），但文字全重叠。

### 第 3 版（用户报"文字位置变了"，实为整体缩小）
在第 2 版基础上给 text 坐标叠加 node g 的 translate。**踩坑**：正则 `/translate\(([\d.\-]+)[, ]([\d.\-]+)\)/` 的分隔符 `[, ]` 只匹配**一个**字符，而 markmap transform 是 `", "`（逗号+**空格**两个字符）→ 解析失败 tx=0 → 文字仍全叠原点。改用 `,\s*` 修复后，27 个文字坐标正确展开、内容完整进 viewBox（验证：27/27 独立坐标、0 越界、PNG 像素铺满画布）。
**但用户仍不满意**：此时 viewBox = 数据坐标包围盒、width/height = 包围盒（不乘 k）→ **整棵树以数据坐标 1:1 导出（文字 12px），比屏幕 fit 后（约 ×2）小一半** → "文字位置都变了"（实为整体缩小、观感大变）。

### 第 4 版（当前代码，用户仍报"还是不行"）
在第 3 版基础上**保留主 zoom 层的 `scale(k)`、只去掉 `translate`**；`viewBox` = 数据坐标包围盒，`width/height` = 包围盒 × k；文本坐标 = node translate + 局部（数据坐标）；PNG 仍 3×。
程序化验证全部通过：k 保留（放大后 k=2.5）、w/vb = k（无二次缩放）、27/27 独立坐标、viewBox 完整含全部内容、PNG 13832×6935 高清、零 pageerror。
**但用户验收仍失败**："还是不行"。

## 5. 当前状态疑点（为何第 4 版仍不被接受）

程序化几何验证全部通过，但用户视觉验收失败。可能方向（供接手者排查）：

1. **PNG 实际绘画内容有误**：`mmExportPng` 用 Image 载入 SVG Blob 光栅化。SVG 里保留了 `scale(k)` transform 在 zoom 层，而 **`img.naturalWidth` = width 属性 = 包围盒×k**，drawImage 按该尺寸铺画布 —— 理论上内容正好填满。但若 Image 解码 SVG 时**不应用 ancestor `scale()` 于 getBBox 无关的字体渲染**，或 foreignObject 转换的 `<text>` 在 `text-anchor`/`dominant-baseline` 上有视觉偏移，实图可能文字错位。**建议：人工打开导出的 SVG/PNG 目视确认后再谈方案。**
2. **用户看的是 PNG/SVG 默认打开器的渲染**：macOS 预览 / Chrome 对 `<text>` 的字体差异（页面用了 `-apple-system` 等）会导致文本宽度变化 → 长文本溢出右缘。
3. **文字与圆点的垂直对齐**：`text y = nodeTy + foY + font-px×0.8`。markmap 的 `fo y` 语义需确认为「顶部/中心」，0.8 系数是经验值，可能有 ±几像素错位，视觉上"文字位置变了"。
4. **换一种实现思路（推荐优先考虑）**：
   - **方案 A**：导出时**完全不用 markmap 的 transform 体系**——clone 后把 zoom 层 transform 移除，给 svg 外部套 `<svg viewBox=内容bbox>`，用 CSS 缩放全图（最简单粗暴：`.`markmap-zoom{transform:scale(k)}` 也行不通时考虑整体换方案）；
   - **方案 B**：改用 `dom-to-image`（massCode 官方导出就用它，DOM 级截图，天然所见即所得而不受 SVG transform 困扰）：`dom-to-image.toPng/toSvg` 作用于 `#mm-stage`（含 svg 的容器），对容器做 `width/height` 临时展开（拿到 markmap `MM_OBJ.state.rect` 数据 bbox 后换算容器尺寸），这最贴近 massCode 原版行为；
   - **方案 C**：markmap-view 自带 `Markmap toSVG` 无官方导出；但 markmap-lib 有 `Transformer` 的 `transform` 数据，可另起 canvas/SVG 干净重绘（成本高，不优先）。
5. **markmap 内部状态可用**：`MM_OBJ.state.rect`（数据内容包围盒 `{x1,y1,x2,y2}`）、`MM_OBJ.state.zoom` 不存在（0.18 的 zoom 在 DOM transform 上）。fit 之后 k、translate 均可在主 zoom 层 g 读到。
