# 嵌入式工程化开发规范

## 1. 目标

本规范用于约束 MCU、RTOS、Zephyr 及嵌入式 Linux 项目中的 C/C++ 代码设计、驱动开发和代码评审。核心目标是：

- 硬件变化时，业务代码尽量不改。
- 故障能被检测、记录、传播和恢复。
- 中断、线程、DMA 和缓存之间的边界明确。
- 模块可以独立测试、替换和复用。
- 重要决策有依据，不依赖隐含经验。

## 2. 规则等级

| 等级 | 含义 | 处理方式 |
| --- | --- | --- |
| 必须 | 涉及安全、内存、并发、硬件时序或可恢复性 | 评审不通过不得合入 |
| 应当 | 默认采用的工程做法 | 偏离时记录原因 |
| 建议 | 根据项目规模和资源选择 | 由团队统一决定 |

行宽、大括号风格、注释语言和函数行数属于团队风格，不应与安全规则混为一谈。

## 3. 阅读顺序

1. `01-架构分层与依赖规则`：确定代码应该放在哪一层。
2. `02-C设备模型与驱动接口`：统一设备对象、ops 和硬件实例。
3. `03-初始化生命周期与错误处理`：规范创建、启动、降级和释放。
4. `04-中断并发与实时性`：约束 ISR、线程和事件传递。
5. `05-内存栈DMA与Cache安全`：检查边界、所有权和 DMA 一致性。
6. `06-代码评审与发布检查清单`：合入与发布前执行。

## 4. 基本工作流

```text
明确需求与时序
  → 确定分层与所有权
  → 定义接口和错误语义
  → 使用 Mock/PC 验证通用逻辑
  → 接入真实硬件
  → 压力、故障注入和长时间测试
  → 评审清单
  → 留存测量记录后发布
```

## 5. 使用边界

本规范不替代以下资料：

- MCU Reference Manual 和芯片 Errata。
- RTOS、HAL、编译器和链接器的当前版本文档。
- 电气、EMC、功能安全和产品认证要求。
- 经过测量得到的项目实际时序与资源数据。

文档中的阈值和方案是默认基线，不是替代测量的绝对结论。
