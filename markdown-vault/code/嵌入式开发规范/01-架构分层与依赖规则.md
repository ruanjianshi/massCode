# 架构分层与依赖规则

## 1. 标准分层

```text
应用层           业务状态机、策略、产品逻辑
中间件/服务层    协议、存储、设备组合、通用算法
设备驱动层       具体器件逻辑，仅依赖总线/Platform接口
Platform层       设备模型、RTOS抽象、总线、自动初始化
Board/HAL层      引脚、时钟、DMA、IRQ、寄存器和芯片库
```

## 2. 强制依赖规则

1. 每层只能调用直接下层或经过评审的稳定公共接口。
2. 应用层不得直接调用 `HAL_*`、芯片寄存器或板级 GPIO 宏。
3. 通用驱动不得硬编码端口、引脚、总线号、设备地址和中断号。
4. Board 层是物理连接关系的唯一真实来源。
5. 上层不得依赖下层的私有结构和全局变量。
6. 跨层调用必须说明它隔离了什么变化，否则视为架构泄漏。

## 3. 硬件配置外置

编译期固定配置放在 `const config`、Board 文件或 Device Tree；运行期状态放在对象的 `data` 中。

```c
struct temp_sensor_config {
	struct i2c_bus *bus;
	uint16_t address;
	uint32_t irq_pin;
};

struct temp_sensor_data {
	int32_t last_millidegree;
	uint32_t error_count;
	bool initialized;
};
```

禁止在驱动中使用“先跑起来再说”的魔法数字。硬件资源必须能追溯到原理图、Device Tree 或 Board 配置。

## 4. 总线与 Client 分离

- Bus 管理控制器、互斥、DMA、超时和传输。
- Client 管理设备地址、寄存器语义和业务数据。
- 同一总线上的设备必须共享同一个锁与错误恢复机制。
- Client 不得自行重置整条总线，应向 Bus 层申请恢复。

## 5. 避免过度抽象

新增一层之前回答：

1. 它隔离的变化是什么？
2. 是否已有 RTOS、Zephyr、RT-Thread 或 Linux 标准接口？
3. 新层是否只做了同名函数转发？
4. 是否能通过替换底层实现证明它的价值？

如果系统已提供稳定设备模型，优先直接使用，不重复包装。

## 6. 架构验证

- 将真实 HAL 替换为 PC Mock，通用驱动应能编译和测试。
- 更换一块主板，业务文件应无需修改。
- 新增一个同类设备实例，应只新增配置和实例，不复制驱动逻辑。
- 搜索应用层的 `HAL_`、寄存器名和板级引脚宏，结果应为零。
